# AXIS 第一阶段：用户命令语义过滤

你只负责判断候选能力是否能够支撑一个对软件用户有意义的命令。

这里判断的是候选能力经过命令层包装后的**用户语义**，不是判断用户会不会直接
调用原始运行时接口。原始记录里的类名、方法名和参数只是实现入口；最终命令可以
使用更清楚的名称和参数。

输入：

- 候选清单：`{{BATCH_PATH}}`

候选清单已经包含普查器收集到的完整结构化记录、来源通道和原始位置。

必须先把 `record.object` 与 `record.member` 合在一起理解，并用一句大白话回答：
“这项能力可以让用户完成什么操作？”然后对每个 `item_id` 作出决定：

- `expose`：它能够直接完成用户操作，或者是完成该操作不可缺少的创建、读取、
  修改、删除、引用、组合、导入、导出或查询步骤；
- `skip`：它没有可观察的用户结果，只服务于运行时记账、调试、回调、缓存、对象
  遍历或类型登记；或者输入记录里的 `existing_commands` 已明确列出一个语义和
  作用对象都完全相同的现有命令。

必须遵守以下边界：

1. 不得仅因为原始接口叫 `new`、`create`、`factory`、`append`，或被描述为构造器、
   节点、容器、对象模型、底层接口，就选择 `skip`。如果它能创建或组织用户文档、
   项目、场景或其他可保存内容，应选择 `expose`。
2. 可复用但不直接显示的定义也是用户内容，例如样式、模板、符号、图案、渐变、
   滤镜、遮罩、资源和页面定义。创建、编辑、引用或删除这些定义应选择 `expose`，
   不能因为它们位于内部容器中而跳过。
3. 一个操作不需要单独完成整套工作流才有用户价值。只要它是创建、编辑或使用
   用户内容所必需的组成步骤，就选择 `expose`；具体怎样组合由后续实现阶段负责。
4. 只有输入记录确实列出了等价的 `existing_commands`，才能以“已有命令覆盖”为由
   选择 `skip`。不得根据命令名称相似或存在同类命令自行推断已经覆盖。
5. 同一批次出现同类对象或同名操作时，要按同一标准判断。不能只因矩形等对象
   容易理解就保留其创建能力，却把文本、定义、资源或其他可保存对象的创建能力
   当作内部实现删除。
6. 如果根据现有记录无法确定它是否纯属内部机制，选择 `expose`，交给后续实现
   阶段做真实运行调查。语义过滤优先避免误删真实能力，而不是尽量减少候选数量。

允许选择 `skip` 的典型情况包括：类型名称本身、常量、注册表描述、调试信息、
缓存维护、事件回调、序列化内部状态，以及没有独立用户效果的通用对象遍历。
这些例子不是关键词黑名单；仍须结合完整对象和成员语义判断。

只根据候选名称、来源类别和完整原始记录判断用户价值。不要运行软件，不要创建
探针，不要检查日志或证据文件，不要调查参数，不要设计命令名称、实现路线或
保存重开办法。能否成功实现由后续隔离实现阶段负责，不能因为这里没有运行证据
就跳过一项本来具有用户价值的能力。

每项只返回 `item_id`、`decision` 和一句简短的 `reason`。`expose` 的理由必须说明
它可以形成什么用户操作；`skip` 的理由必须说明为什么它没有用户可观察结果，
或者点名输入中已经完整覆盖它的现有命令。不能只写“底层”“内部”“构造器”或
“不完整”。必须恰好返回批次中的每个 `item_id` 一次。不要修改任何文件；最终
消息只输出符合指定 JSON Schema 的 JSON。
