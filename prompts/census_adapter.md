# S1 普查适配器编写 Prompt（软件无关模板）

> 用法：把 {软件名}、{运行时启动方式} 等占位符替换掉，整段交给一个 coding agent 执行。
> 本 prompt 固化的是"怎么为一个新软件写普查适配器"这件事；
> 普查产物（raw_ops.json）的生成过程本身运行时零 LLM——数字必须全部来自引擎自报。

---

## 任务

为 {软件名} 实现 S1 能力普查适配器，枚举该软件运行时自报的能力全集，
产出 `AXIS/apps/{软件名}/census/raw_ops.json`。你写的是一次性适配代码：
跑通后冻结进仓库，之后换版本、换机器，任何人重跑脚本即可，不再需要模型。

## 开工前先读（不许跳过）

1. `AXIS/METHOD.md` 的 §S1、§S1.5、附录 A —— 多通道并集+对账的设计动机、
   四软件实测样例。不理解动机就会写出单通道的残次品。
2. `AXIS/apps/libreoffice/census.py` —— 参考实现。输出 JSON 结构、控制台
   汇总风格、reconciliation 写法全部向它对齐。
3. `AXIS/axis/census.py` 与 `AXIS/apps/{软件名}/runtime.json` —— 分发器怎样按
   已探明的命令模板运行你的 Collector。不要修改分发器。

## 第一步：环境冒烟（先探再写）

写任何正式代码前，先回答并实测三个问题（把答案写进适配器的 docstring）：

1. 这个软件的查询和执行入口怎么无人工交互地运行？（命令行登记表、动作 shell、
   内嵌脚本、外部桥、扩展清单等都可以）
2. 每类数据从哪个真实入口取得？不要求代码进入软件进程，也不要求只有一个入口。
3. 上面每个候选通道的最小调用是什么？逐个在交互环境或一次性脚本里冒烟，
   确认能返回数据，再合并成正式 census.py。`census.py` 就是由你编写的
   Collector；核心流程不会替你写死查询方法。

## 第二步：实现六个通道（语义定义软件无关）

每个通道回答一个固定问题。括号里是"在陌生软件上怎么找到它"的判据，
判据是通用的，具体 API 因软件而异：

- **A 调度表**：这个软件执行一个操作时，查的是哪张表？
  判据：不在这张表上的操作 = 引擎执行不了。命令注册表 / 过程数据库 /
  算子表 / 算法注册表，一定有一张。全量枚举它。**这张表就是构造完备的
  依据**，找到它就找到了完备性锚点。
- **B 引擎花名册**：引擎有没有自报"我能造哪些类型/服务"的出口？
  判据：通过当前安装软件公开的查询入口或正式安装登记物取得全表（类型模块枚举 /
  服务工厂列表 / 扩展登记 / 各类注册表）。有多个注册表就全列。
- **C 文档花名册**：一份文档/项目文件里能装哪些种类的对象？
  判据：文档对象工厂的自报名单 / 数据容器集合 / 文档类型枚举。
- **D 菜单声称**：GUI 菜单树声称了哪些操作？
  判据：菜单配置管理器 / 菜单类注册表 / 插件菜单缓存文件。GUI 结构在
  无头环境下画不出来时，先试虚拟显示；仍不行就进 unavailable，附具体
  错误，**不许用文档或猜测补数**。
- **E 成员普查（递归）**：对象有没有成员反射？成员 = 属性**和方法**，两者都要。
  判据：属性集信息 / RNA / 元对象 / GIR / 方法表 / 过程签名。反射机制不存在
  就如实进 unavailable。

  这个通道有三条硬要求，缺一条整个普查作废。它们不是风格偏好，是因为
  旧版本只做"挑几个代表对象、列属性名、报个数"，结果一个软件里 492 个
  对象方法躺在普查结果里从没变成命令，Agent 拿不到"取单元格""插一行"
  这类最基本的零件：

  **E-1 逐条落盘，不许只报数量。** 每个成员必须单独一条记录，带完整签名：

  ```json
  {"object": "<对象类型名>", "member": "<成员名>", "kind": "property|method",
   "params": [{"name": "...", "type": "<软件自报的类型名>"}],
   "returns": {"type": "<软件自报的类型名>", "is_object": true|false},
   "writes": true|false, "universal": true|false,
   "reached_from": "<从根对象走到这里的路径>"}
  ```

  `params[].type` 和 `returns.type` 必须是软件自报的真实类型名。写
  `"unknown"`、空字符串或省略，等于把类型信息丢掉——后面就只能靠成员名
  去猜它能不能调用，那正是旧版本失败的原因。

  **E-2 沿着"返回对象"的成员递归展开。** 不要停在根对象的第一层。
  `returns.is_object` 为真的成员，要试着真的拿到那个对象实例，然后继续
  枚举它的成员。用**对象类型**去重（同一类型只展开一次），不用实例去重。

  为什么必须递归：一个表格单元格通常不挂在文档上，而是
  文档 → 表格集合 → 某个表格 → 行集合 → 单元格，四层。只展开一层就
  永远看不到 `setString`（给单元格写字）这种成员。仓库里
  `experiments/recursive_discovery/REPORT.md` 记录了六个软件上的实测，
  递归展开在每一个上都找到了旧普查漏掉的关键操作。

  **E-3 展不开的必须落边界账，不许静默消失。** 声称返回对象但实际拿不到
  实例的成员，写进 `channels.members.boundary`，附上失败原因。等式必须成立：

  ```
  展开成功的对象类型数 + 边界账条数 = 声称会返回对象的类型总数
  ```

  等式不成立说明有东西悄悄丢了。这条等式是"没漏"唯一的机械证据，
  自己在脚本里算出来打印，不要让下游去猜。
- **F 类型抽查**：从官方文档挑 3-4 个已知类型名 + 编 1 个必然不存在的
  假名，逐一向运行时点名（存在性解析），真名应全过、假名应被拒；
  顺带回答：**类型树能不能整棵枚举**（能/不能，证据是什么）。

找不到某通道的等价物：进 `unavailable` 附原因。通道不齐不是失败，
**编数字才是**。

## 第三步：对账（reconciliation）

至少取两个独立通道做交集对账（首选 D 菜单声称 vs A 调度表）：

- 交集数量、A 对 D 的覆盖率；
- 两侧差集**全量列出**（菜单声称但调度表没有 / 调度表有但菜单没声称），
  附分诊（结构性占位 vs 真候选），不许静默丢弃；
- 对 A 做存在性回查（注册项逐条回查可解析，记录失败数）。

对账覆盖率本身是重要产出（四软件实测 63.5%～100% 不等，是软件指纹），
不要追求数字"好看"，追求数字真实。

## 输出契约（与参考实现对齐，不许改结构）

```
{
  "app": "{软件名}",
  "engine_version": "...",        // 引擎自报版本
  "channels": {
    "dispatch": { ... },          // A 调度表
    "engine_roster": { ... },     // B 引擎花名册
    "document_roster": { ... },   // C 文档花名册
    "menu": { ... },              // D 菜单声称
    "members": {                  // E 成员普查（递归），结构固定如下
      "records": [ ... ],         //   逐条成员记录，字段见 §E-1
      "boundary": [               //   展不开的，见 §E-3
        {"object": "...", "member": "...", "declared_type": "...",
         "reason": "..."}
      ],
      "expanded_types": 0,        //   成功展开的对象类型数
      "declared_object_types": 0, //   声称会返回对象的类型总数
      "max_depth": 0,             //   递归最深层数，必须 ≥ 2
      "count": 0                  //   records 的条数
    },
    "type_spotcheck": { ... }      // F 类型抽查
  },
  "reconciliation": { ... },
  "unavailable": [ {"channel": "...", "reason": "..."} ]   // 无则空数组
}
```

`channels.members` 的结构是固定的，不许改字段名——`axis/conformance.py` 和
下游的账本、探针都按这个结构读。其余通道的内部结构可以随软件。

落盘 `apps/{软件名}/census/raw_ops.json`；控制台打印 "=== 普查汇总 ==="
风格 A–F 逐行计数 + 对账结果（照参考实现的样子）。

## 验收（全部满足才算完）

前四条自己跑，第五条由独立脚本判——**你说通过不算通过，脚本说通过才算**：

1. `cd AXIS && python3 axis/census.py --app {软件名}` 退出码 0，分发器
   末尾打印完成行；
2. raw_ops.json 可被 json.load，通道齐全或不可用者在 unavailable；
3. 计数恒等式自洽（分组之和 = 总数；交集 + 两侧差集 = 两侧总数）；
4. 重跑结果确定（全量排序输出，无随机性）；
5. `python3 axis/conformance.py --app {软件名}` 全项通过。它检查的东西你
   骗不过去：成员记录的类型名是不是真的填了、递归有没有展开到两层以上、
   边界账等式成不成立、重跑是不是确定。哪项不过，它会打印具体哪条记录、
   缺哪个字段——照着改，不要放宽标准。

## 铁律

- 收集时零 LLM：每个数字必须来自当前安装软件的真实返回或正式登记物，不许编造、不许抽样
  冒充全量（除非全量成本确实不可行，且必须在 JSON 里注明是抽样）；
- 只枚举，不分类：语义归类是 S2 的事，普查保持原始词汇原样落盘；
- 不可用通道进 unavailable 附具体错误，这是给后续开发的缺口清单，
  不是耻辱；
- 只写 `apps/{软件名}/` 下的文件，不动 axis/、其他 apps、文档；
- 不联网。
